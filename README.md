# Turborepo Monorepo Starter

A Bun-powered monorepo with a React frontend, a Go backend, shared configuration packages, and
Turborepo orchestrating the task graph.

- **Frontend** — `apps/web`: React 19 + TypeScript, Tailwind CSS v4, TanStack Router + Query, built with Vite.
- **Backend** — `apps/api`: Go + Gin with graceful shutdown and hot reload via [air](https://github.com/air-verse/air).
- **Shared config** — `packages/*`: TypeScript base config, oxlint config, oxfmt config.

## Requirements

| Tool | Version    | Notes                                                   |
| ---- | ---------- | ------------------------------------------------------- |
| Bun  | `>= 1.2`   | package manager + workspace runner                      |
| Go   | `>= 1.25`  | API runtime                                             |
| Node | `>= 20.19` | only needed as a fallback runtime for some tools        |
| air  | latest     | optional, but used by `bun run dev` for `apps/api`      |
| make | any        | optional — every script is also available via `bun run` |

```bash
# install air once (writes to $(go env GOPATH)/bin)
go install github.com/air-verse/air@latest
```

## Getting started

```bash
bun install          # installs all workspaces and registers the git hooks
bun run dev          # runs apps/web and apps/api in parallel
```

Or use the `Makefile`, which wraps every root script (see `make help`):

```bash
make setup           # bun install + git hooks
make dev             # runs apps/web and apps/api in parallel
```

- Web: http://localhost:3000
- API: http://localhost:8080 (`/tutorial-api/health`, `/tutorial-api/hello`, `/healthz`)

Vite proxies `/tutorial-api/*` to the Go server, so the frontend can call the API with relative URLs during
development. Override the proxy target with `VITE_API_PROXY_TARGET`, and the production API origin
with `VITE_API_URL`.

│   │   ├── .air.toml

│       ├── public

│           ├── lib          # API client
│           └── routes       # TanStack file-based routes

│   ├── oxfmt-config         # shared .oxfmtrc
│   ├── oxlint-config        # shared .oxlintrc (base + react)

`apps/web/src/routeTree.gen.ts` is generated by TanStack Router — from the Vite plugin during
`dev`, or from `tsr generate` during `build`/`typecheck`. It is gitignored, so it never shows up in
diffs.

## Commands

Run from the repo root — Turborepo fans each task out to the relevant workspaces. Every target is
available both as a root `bun run` script and as a `make` target.

| `make`              | `bun run`              | Description                                   |
| ------------------- | ---------------------- | --------------------------------------------- |
| `make install`      | —                      | Install all workspaces (also installs hooks)  |
| `make hooks`        | `bun run prepare`      | Install/refresh the Lefthook git hooks        |
| `make dev`          | `bun run dev`          | Start every `dev` task (web + api)            |
| `make dev-web`      | —                      | Start only the web dev server                 |
| `make dev-api`      | —                      | Start only the API (air hot reload)           |
| `make build`        | `bun run build`        | Build all workspaces                          |
| `make build-web`    | —                      | Build only `apps/web`                         |
| `make build-api`    | —                      | Build only `apps/api`                         |
| `make preview`      | —                      | Serve the production web build                |
| `make start-api`    | —                      | Build and run the compiled API binary         |
| `make generate`     | —                      | Regenerate the TanStack Router route tree     |
| `make lint`         | `bun run lint`         | `oxlint` for TS/TSX, `go vet` for Go          |
| `make lint-fix`     | `bun run lint:fix`     | Apply safe oxlint fixes                       |
| `make format`       | `bun run format`       | `oxfmt` for the repo, `gofmt` for Go          |
| `make format-check` | `bun run format:check` | Fail if anything is unformatted (CI friendly) |
| `make typecheck`    | `bun run typecheck`    | `tsc --noEmit` for TS, `go build` for Go      |
| `make test`         | `bun run test`         | Run every test suite                          |
| `make test-api`     | —                      | Run only the Go tests                         |
| `make check`        | —                      | format-check + lint + typecheck + test        |
| `make clean`        | —                      | Remove build output and generated files       |
| `make clean-all`    | `bun run clean`        | As above, plus `node_modules`                 |
| `make versions`     | —                      | Print bun / go / turbo versions               |

Scope a Turborepo-backed target to one workspace with `FILTER`:

```bash
make dev   FILTER=@repo/api
make build FILTER=@repo/web
make lint  FILTER=@repo/web
```

Or call Turbo directly:

```bash
bunx turbo run dev --filter=@repo/api
bunx turbo run build --filter=@repo/web
```

## Tooling

### Formatting and linting

Both oxc tools read a shared config from `packages/` so every workspace stays consistent:

- `oxfmt` — `packages/oxfmt-config/index.json`, passed via `-c`. Configured with `sortImports` and
  `sortPackageJson` so imports and `package.json` keys are ordered automatically.
- `oxlint` — `packages/oxlint-config/index.json` (base) and `react.json` (React + jsx-a11y). Each
  workspace opts in through a local `.oxlintrc.json` that `extends` the shared file.

Go files are formatted with `gofmt` and checked with `go vet`.

Both oxc tools honor `.gitignore`, so build output (`dist/`, `bin/`, `.turbo/`) and generated files
are skipped automatically.

> Config changes in `packages/*` are listed in `turbo.json#globalDependencies`, so Turbo correctly
> invalidates cached lint and typecheck tasks when a shared config changes.

### Git hooks

[Lefthook](https://lefthook.dev) runs on every commit (hooks are installed by `bun install`):

- **pre-commit** — formats and lints only the staged files, then re-stages the fixes:
  - `oxfmt --write` for JS/TS/JSON/CSS/Markdown
  - `oxlint --fix` for JS/TS
  - `gofmt -w` and `go vet` for Go
- **commit-msg** — enforces [Conventional Commits](https://www.conventionalcommits.org)
  (`feat`, `fix`, `docs`, `chore`, …).

Re-install the hooks manually with `bun run prepare`.

## Environment variables

Copy `apps/api/.env.example` to `apps/api/.env` and adjust as needed:

| Variable        | Default                 | Description                                                          |
| --------------- | ----------------------- | -------------------------------------------------------------------- |
| `APP_ENV`       | `development`           | `development` / `staging` / `production`                             |
| `PORT`          | `8080`                  | HTTP port (serves the API and, with `WEB_DIR`, the SPA)              |
| `ALLOW_ORIGINS` | `http://localhost:3000` | Comma-separated CORS allow list                                      |
| `WEB_DIR`       | _empty_                 | Directory of a built SPA to serve; empty disables it                 |
| `WEB_BASE_PATH` | _empty_                 | URL prefix the app is mounted under (e.g. `/tutorial`); empty = root |

## Docker

One image is defined at the repository root (`Dockerfile`):

- stage 1 — Bun builds the SPA into `dist`
- stage 2 — Go compiles a static binary
- stage 3 — `alpine` runs the binary with the SPA at `/app/public`

The Go server serves **both** the API and the frontend (`WEB_DIR`), so production is a single
process on a single port. Run it locally:

```bash
make docker-up      # docker compose up -d --build  (http://localhost:8080 + /tutorial/)
docker compose logs -f
make docker-down
```

The SPA is built for a `/tutorial/` mount (`VITE_BASE_PATH`, default `/tutorial/`) to match the host
nginx, and the Go server accepts requests under both `/` and `/tutorial/...` (`WEB_BASE_PATH`), so
the container works with or without a prefix-stripping proxy. Override the mount when building for
the domain root:

```bash
docker build --build-arg VITE_BASE_PATH=/ -t ali-ecs-docker-build-tutorial:latest .
```

The image is named `ali-ecs-docker-build-tutorial` — it is the whole application, since the Go
server serves the SPA as well as the JSON API.

`docker-compose.yml` is the **production** file (image name only, no build context).
`docker-compose.override.yml` adds the local build context and is merged automatically by docker
compose; it is never copied to the server. The container binds to `127.0.0.1` only — the host nginx
is the public entry point.

Gone compared to the two-image setup: the `nginx` sidecar, its `apps/web/nginx.conf`, and the second
build/push. The cache headers that config set are now emitted by the Go static handler. The one
thing still worth putting in the host nginx is `gzip on;` (the Go server does not compress).

## Deployment (GitHub Actions → Aliyun ECS)

`.github/workflows/deploy.yml` runs on every push to `main`:

```
GitHub push -> lint & test -> docker build -> push to ACR (latest + github.sha)
            -> SSH to ECS -> docker login ACR -> docker pull -> compose up -d -> health check
```

One image is built and pushed, so there is exactly one ACR repository to create
(`ali-ecs-docker-build-tutorial`).

Required secrets — stored in the GitHub environment named **`prod`**
(_Settings → Environments → prod_), which the `build` and `deploy` jobs declare. Repository-level
secrets work too and are simpler if you'd rather not scope them:

| Secret         | Value                                                                                                                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ECS_HOST`     | Public IP of the ECS                                                                                                                                                                            |
| `ECS_USER`     | SSH user (`root` or a deploy user)                                                                                                                                                              |
| `ECS_SSH_KEY`  | Private key whose public key is in `~/.ssh/authorized_keys`                                                                                                                                     |
| `ECS_PORT`     | SSH port (optional, defaults to `22`)                                                                                                                                                           |
| `ACR_REGISTRY` | Registry **including the namespace**: `registry.cn-hangzhou.aliyuncs.com/my-namespace`, or for a personal/enterprise instance `crpi-xxxxxxxx.cn-shanghai.personal.cr.aliyuncs.com/my-namespace` |
| `ACR_USERNAME` | ACR access credential username                                                                                                                                                                  |
| `ACR_PASSWORD` | ACR access credential password                                                                                                                                                                  |

> Environment secrets are only readable inside jobs that declare that environment, and they
> **cannot** be referenced from workflow-level `env:`. The workflow therefore defines
> `IMAGE_WEB`/`IMAGE_API` at job level, not at the top of the file.

### Troubleshooting

| Symptom                                              | Cause                                                                                        |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `Username and password required` (login step)        | Secret missing or an environment secret not visible to that job                              |
| `denied: requested access to the resource is denied` | `ACR_REGISTRY` lacks the namespace (`<host>/<namespace>`), or the ACR repo doesn't exist yet |
| `unauthorized: authentication required` at login     | Wrong ACR credentials (RAM AccessKey pair instead of ACR Access Credentials)                 |
| `invalid reference format`                           | `ACR_REGISTRY` contains a scheme (`https://`)                                                |

The `Verify ACR access before push` step fails the job only on configuration errors — a missing
namespace in `ACR_REGISTRY`, or a VPC-only endpoint. Its registry probe performs the same
bearer-token handshake as `docker push` and reports the outcome (readable / repo missing / no
access), but it is **advisory**: a repository endpoint also answers `401`/`404` for a repo that has
simply not been created yet, and ACR creates repos on first push, so the push itself remains the
authoritative test.

On the ECS, once: install Docker + the compose plugin and create `~/app/.env` with
`ALLOW_ORIGINS=https://your-domain.com`. One private ACR repository
(`ali-ecs-docker-build-tutorial`) must exist under the namespace.

Host nginx (already terminating SSL) forwards to the single container — the SPA and the JSON API
share one port. The ECS exposes the app under `/tutorial/`, so mount it there; the trailing slash on
`proxy_pass` strips the prefix before forwarding:

```nginx
# optional but recommended: the Go server does not compress responses
gzip on;
gzip_types text/css application/javascript application/json image/svg+xml;

location /tutorial/ {
    proxy_pass http://127.0.0.1:8080/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

To serve the app from the domain root instead, proxy everything and build the image with
`--build-arg VITE_BASE_PATH=/`:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

The Go server is prefix-aware, so even a root proxy works with the default `/tutorial/` build:
asset and API requests under `/tutorial/...` are resolved against the same files and routes.

Because everything is same-origin, `ALLOW_ORIGINS` mainly matters if you also call the API from
another domain; `WEB_DIR=/app/public` is what enables the SPA and is already set in the image.

Only ports `22`, `80` and `443` need to be open in the Aliyun security group.

## Adding a package

```bash
mkdir packages/my-lib && cd packages/my-lib
bun init -y
```

The `apps/*` and `packages/*` globs in the root `package.json` pick it up automatically. Reference
it from another workspace with `"@repo/my-lib": "workspace:*"`.
